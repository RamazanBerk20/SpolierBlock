# How it works

This page describes the browser extension (version 0.2.4). The Android port is in [android.md](android.md). It follows the same rules. The config, the decision rule and the cover wording are defined in [agents/contract.md](agents/contract.md) and are not repeated here.

## Overview

```
page  <->  content script  --messages-->  background  -->  engine (title model, OCR, classifier)
(every     |  matcher (text)               |  catalog search, catalog update, index rebuild
 frame)    |  covers, media scan           |  Firefox: event page runs the engine itself
           v                               |  Chrome: service worker + offscreen document
     storage.local  <------  settings page (own tab), popup (quick panel)
```

| Piece | File | Job |
|---|---|---|
| Content script | `src/content/content.js` | Finds posts, runs the matcher, applies the decision rule, draws covers, sends images to the background. |
| Matcher | `src/content/matcher.js` | Hash-index text matcher. Loaded before the content script. |
| Page styles | `src/content/content.css` | Hides the page until ready, dims unscanned media, hides covered content. |
| Background | `src/background/background.js` | Routes messages, catalog search, catalog update scheduling, index rebuild, 0.1 migration, shortcut and badge, starts the engine. |
| Engine | `src/background/engine.js` | Title check, OCR, spoiler classifier, title-in-context model, priority queue. |
| OCR module | `src/background/ocr.js` | PP-OCR detection and recognition on onnxruntime. Pure functions, also run by Node tools and tests. |
| Offscreen page | `src/background/offscreen.html`, `offscreen.js` | Chrome only. Hosts the engine. |
| Catalog update | `src/background/catalog-update.js` | Opt-in Wikidata refresh, and the index rebuild that also indexes hand-added works and the user's extra names (`learned.names`). |
| Settings page | `src/options/` | Library, Add by hand, Corrections, Blocking, Data, About. Opens in its own tab (`options_ui` with `open_in_tab`). `config.js` holds the pure config functions (migration, import, export). |
| Popup | `src/popup/` | Quick panel: cover count of the page, pause on this site, cover caption-less videos on this site, the page's text selection as a new name for a work, search and mark as seen, link to the settings page. |
| Shared rules | `src/shared/build-index.js`, `catalog-rules.js`, `context-input.js` | Index builder, catalog rules, and the title-in-context model's input (window, segment B, token ids). Used by Node and by the extension; `context-input.js` is also a content script (`globalThis.SBContext`), loaded after the matcher. |

### Background: Firefox and Chrome

- **Firefox.** `manifest.json` declares a module background script (an event page). It imports `engine.js` in place, so the models run in that page. Firefox extension pages cannot be cross-origin isolated, so the models run on one thread. The event page may be asleep when a content script sends a request, so the content script retries engine requests a few times when it gets "Receiving end does not exist".
- **Chrome.** `tools/build.mjs` rewrites the manifest: the background becomes a module service worker, `offscreen` is added to the permissions, and COEP/COOP are set. Service workers cannot host the WASM runtime, so the worker creates an offscreen document (reason `WORKERS`) from `src/background/offscreen.html`. It forwards inference messages to that document with `target: 'offscreen'`. Cross-origin isolation (`cross_origin_embedder_policy: require-corp`, `cross_origin_opener_policy: same-origin`) gives that document `SharedArrayBuffer`. The engine then uses `min(4, hardwareConcurrency)` WASM threads.
- The build removes `offscreen.html` and `offscreen.js` from the Firefox output. There is no `browser` shim any more: pages use `globalThis.browser ?? globalThis.chrome`.

Message listeners, the alarm listener and the command listener are registered synchronously, so an alarm can wake a suspended page.

## Content script

It runs at `document_start` in every frame (`all_frames`, `match_about_blank`). An `about:blank` or `srcdoc` frame takes its host name from its parent.

1. **Gate.** `content.css` keeps `body` invisible until the matcher is loaded and the first scan ran (`data-sb-ready` on `<html>`). A 2.5 second timer sets the attribute anyway, so a failure never leaves a page blank.
2. **Observe.** A `MutationObserver` collects changed text nodes, `alt` and `aria-label` attributes (set or changed in place: YouTube relabels its end-screen cards), every added element that carries one (a card whose only text is its label has no text node to queue it), images, videos and elements with an inline `url(...)` style. It runs before paint. It also watches open and closed shadow roots, including roots attached after the element was first seen (a custom element that is not yet defined is retried for 30 seconds).
3. **Find the block.** For each changed text it walks up (through shadow boundaries) to a "post-like" container. Site selectors exist for X (posts, user cells, trends, DM rows and conversations, search suggestions, hover cards), YouTube (video and comment renderers, notifications, live chat messages, and the player's own cards: end-screen stills `.ytp-videowall-still` and `.ytp-modern-videowall-still`, end cards `.ytp-ce-element`, the autoplay card `.ytp-autonav-endscreen-upnext-container` and the pause overlay's `.ytp-suggestion-link` / `.ytp-suggestion-set`; these sit inside the player, outside every renderer, and without them a card's title box alone was covered and a card labelled only by `aria-label` not at all) and Reddit. Everywhere else a generic list is used: `article`, `li`, `figure`, `blockquote`, role `article`, `row`, `listitem` or `option`, and class names containing `card`, `post`, `tweet`, `comment`, `message`, `item` or `entry`. That list is what covers direct messages, notification lists and search suggestions on other sites. A container with more than 3,000 characters of text is treated as a page section, not a post.
4. **Read the block.** Text nodes joined by newlines, plus `alt`, `aria-label` and `title` attributes of the block and of everything in it (the block's own label since 0.2.4: an end-screen card is often one labelled link), plus text inside shadow roots. The post's own text is read first. Any OCR text of the pictures the block shows now follows it behind one U+0001 character (`own text` + `\u0001` + `OCR text`, contract rule 8). `domText` strips U+0001 from the page's own text, so a page cannot pose as OCR text. On youtube.com a video block's channel name follows the own text behind one U+0002, before any OCR part (contract rule 9; `uploader` in `content.js`): the first non-empty match of `ytd-channel-name #text`, `#channel-name #text`, `#byline`, the end-screen author fields, a link inside a `metadata-row`, or a link to `/@...` or `/channel/...`, cut at " • ". Comment and live chat blocks get none, and no match means no U+0002 part. The channel's text stays in the own text too; there it is the uploader's name like any other occurrence, so it needs media evidence and adds none. `domText` strips U+0002 as well. The text sent to the classifier has both markers replaced by line breaks.
5. **Match.** `matcher.evaluate(text, isSeen)` returns the groups the text is about, own-text groups first, then groups named only by OCR text (see [The matcher](#the-matcher)). Seen groups (contract rule 1: any work seen, none blocked) are dropped. When the block has pictures, the post's own text is also evaluated alone (`own`), so the decision knows what the typed text names.
   - **Unsure names** (contract, "Names the matcher is unsure about"). Right after that `evaluate`, `matcher.unsure(text, isSeen)` gives the names no rule confirmed (at most 4, never a seen group; see [Unsure names](#unsure-names)). For each, `contextGroups` in `content.js` builds segment A from the post's own text and segment B from the group (`src/shared/context-input.js`) and asks the engine (`text.context`). A yes makes the group a matched group of the own text, after the groups the rules accepted (and part of `own`), and the decision rule applies to it unchanged. While a question is in flight the block is decided without that name, so it is not covered for it; the answer re-scans the block only if it is still on the page with the same own text. A failed request is a no. Answers are kept per (segment A, group) for the page, the oldest dropped after 2,000, so the same text is asked once. Each question counts in `data-sb-busy` while in flight and in `stats.ctx` (`data-sb-stats`). The tab title takes the same path.
6. **Decide.** The decision rule of the contract turns groups and picture verdicts into a cover label or nothing (`decide` in `content.js`). Rule 7 is applied here: the image model's title (`img`) is dropped when `own` names any work, seen or not, and per picture when that picture's OCR text names a work; a block whose own text names a seen work and no covered one is not covered by its pictures, and `Possible film, show or game image` is not shown for it. A block is re-decided from what it shows now, not from what it showed before. The text sent to the classifier has the marker replaced by a line break.
   - **Videos with no caption** (contract rule 10, lowest priority). When the site is in `settings.captionlessVideos` (`listed` in `content.js`: the host without `www.`, `mobile.` or `m.`, an entry covering its subdomains, and `x.com` and `twitter.com` read as one site), a block that holds a `video` element (also inside a shadow root) is checked for a caption (`hasCaption`). On x.com the caption is `[data-testid="tweetText"]` with some text; elsewhere it is any run of 4 or more words, a run being the text of one element's own text nodes, not counting text inside a button, `[role="button"]`, `time` or `[aria-hidden="true"]`. A block with no caption whose own text names no work, seen or not (`own`, evaluated without the seen filter), and that no other rule covers gets `Video with no caption`, without "I've seen it". While a site is listed, every added `video` element queues its block, so a post with no text at all and a player added to a post later are scanned too.
7. **Cover.** A `<sb-overlay>` element with a shadow root is added inside the block. It carries the label and the four buttons (Show once, I've seen it, Not this, ⋮). The block's own children get `visibility: hidden`. The cover is a small light or dark panel with a compact one-row layout for short blocks (76 px or less), in which the label is cut first and the three text buttons may shrink with an ellipsis, so all four stay inside a narrow cover. It is dark when the nearest opaque background above the block is dark. When there is none (`isDark` in `content.js`), the canvas colour decides: the page's `color-scheme`, read from the computed property or, when that is `normal`, from `<meta name="color-scheme">` (a meta tag leaves the property at `normal`). A page that allows both schemes follows the system setting; a page that allows only dark is dark under a light system, and the other way round.
   - "Show once" is remembered for the post, not for the element that draws it. It is keyed by the post's own text with every run of digits blanked to `#` (`\d[\d.,:]*`, so a ticking counter keeps the key, as `Scanner.shownKey` does on Android) and whitespace collapsed (never the OCR text), or, for a post whose text has no letter, by the sources of its pictures. The keys live in one set (`shown` in `content.js`) for the life of the page, the oldest dropped after 500. It survives a recycled or rebound node and late picture verdicts. Two posts with identical text share the choice.
   - **The pill.** A post shown once whose decision is still a cover that names works (the decision has `marks`) keeps the same `<sb-overlay>` in a pill state (`apply` passes `pill` to `showOverlay`): the overlay gets `data-pill` and the block `data-sb-pill` instead of `data-sb-blocked`, so its content stays visible and its video is not silenced (a cover that turns into a pill calls `unsilence`). The overlay still fills the block, transparent and with `pointer-events: none`; only the pill in its top corner at the inline end (`inset-inline-end`) takes clicks, so a click on the post elsewhere, a link in it for instance, reaches the page. The pill holds two 20 px text buttons, `Not this` (the cover's action, `notThis`, with the same marks) and `Cover again` (drops the post's key from `shown` and decides again, so the cover returns), at 75% opacity until it is hovered or a button has keyboard focus. Its group is named by the cover's label. In a block 170 px wide or narrower only a `⋯` button shows (named "SpolierBlock: Not this, Cover again", with `aria-expanded`), which opens the two. The pill follows the decision on every scan: it goes when the decision no longer covers or names no works (a work marked seen, a "Not this", a settings change), so a post shown from "Possible film, show or game image" or "Video with no caption" has none. A pill is not counted as a cover for the toolbar badge.
   - "I've seen it" on a name group with one work writes it to `storage.local.works` at once. With several works (a franchise, an original and its remake) it opens the picker (`seenClicked`): a modal `<dialog>` inside the cover's shadow root, so it sits in the top layer and changes no layout. It is titled "Which have you seen?", lists the works not yet seen of every group the cover names with `{type} · {year}`, has nothing ticked at first, and offers All (the first section only), Cancel and Mark seen. A second section, "More from this series" (`moreFromSeries` in `content.js`, which asks `Matcher.moreFromSeries`), lists the other works of the same catalog series that are not yet seen, oldest first, six shown and the rest behind "Show N more", with its own "All N"; ticking them is optional and does not decide whether the post stays covered. The note names the group, or says "This post names several works..." when the cover names several. A group of one work opens the picker only when its series has other works not yet seen (contract, "Cover wording"): the first section is that work, already ticked, with the note `This post is about "{title}". It is shown once you mark that one.`, and the second section is as above; with no such works it is marked at once. Escape closes it and focus returns to the button. Only the ticked works are written, in one call (`markWorks`). Every tab then re-evaluates through `storage.onChanged`. The button is absent for an unidentified image.
   - "Not this" (contract rule 11) writes, for every work of the groups the cover names, a key to `storage.local.learned.not[id]`: `{site}/{source}` when the post's source is known, else `{site}`, lower-case. The site is the host as in `listed` (without `www.`, `mobile.`, `m.`; twitter.com read as x.com). The source is the YouTube channel (`uploader`, the same name rule 9 uses; comments and chat have none) or, on x.com, the author's handle with its `@`, from the first `[data-testid="User-Name"] a[href^="/"]` of the post. `decide` drops a matched group, from text, OCR, the context model or a picture title, before rule 1 when every work in it carries the post's `{site}/{source}` key or its `{site}` key (`notHere`), as if it had not matched; rule 7 and rule 10 then see the remaining groups. The keys are part of the block's scan key. The cover goes at once (the local copy is updated before the write) and the storage change re-judges every tab: the text-keyed caches (classifier verdicts, context answers, "Show once") hold model answers, not decisions, and `rescanAll` decides every block again. Absent, like "I've seen it", for the unidentified image and the video with no caption.
   - ⋮ sends `ui.openSettings`, which opens the settings page in a tab.
8. **Tab title.** `document.title` is replaced by the cover's label while the title names a covered work. This is done in the top frame only.
9. **Pause and disable.** `settings.enabled` and `settings.pausedSites` (a host and its subdomains) switch scanning off live. `settings.captionlessVideos` (the same kind of host list) switches rule 10 on and off live; the settings page edits it under "Cover videos with no caption on these sites" (below the setting for unrecognised images), and the popup has "Cover caption-less videos here" for the current site.
10. **Settings changes.** `rescanAll` re-checks covered blocks in place (`scanBlock(b, true)`), so a cover that stays keeps its element and the keyboard focus inside it; only a block that is gone is released. Then it collects the page again.

### The layout rule

A cover never changes the measured size of anything. Virtualised feeds position posts by measured height, and a box that changes size shifts every post below it. So the cover is absolutely positioned inside its block with `!important` rules and size containment, content is hidden with `visibility`, not `display`, and pending media is darkened with a `filter`. The block gets `position: relative` only when it is static. There is no forced minimum height. A covered block, and a block with a pill, also gets `isolation: isolate` (`content.css`, and `ROOT_CSS` in shadow roots), so the cover's large `z-index` ranks it above the block's own content only: a site's fixed or sticky bar (a bottom navigation, a header) stays drawn above the cover and takes the clicks. The picker is a modal dialog in the top layer and is above everything, as a modal must be.

Verdicts are stored per picture: for each `img`, `video` or background element, the source it showed when it was judged. A cover is recomputed from the text and the verdicts of the pictures the block shows now. A recycled node therefore never keeps the cover of its previous post. A change of the `src`, `srcset` or `poster` attribute always resets the element: Firefox updates `currentSrc` only once the new picture loads, so the attribute is the earlier signal.

The toolbar badge shows the cover count of the top frame. The top frame sends `tab.count` when the count changes. The popup's count asks the top frame only.

### Known limits

Left as comments in `content.js`:

- CSS backgrounds are scanned only when set inline on an element with no element children (X and React Native Web photos). Backgrounds from a stylesheet, and hero sections with content, are not.
- Loose text directly inside a very large container is not covered. It would black out the page.
- Pending media inside shadow roots is not darkened before its verdict. It is covered after the verdict.
- Works added by a catalog update or by hand have no title rows for images, so their images only get the generic verdict.

## Storage contract

All data is in `browser.storage.local`. The settings page, popup, content script and background share it. The shapes of `works`, `custom` and `settings` are in the [contract](agents/contract.md).

| Key | Shape | Written by | Notes |
|---|---|---|---|
| `works` | `{ [id]: { state, style, title, type, year, ts } }` | settings page, popup, content script, import | Only works the user has touched. |
| `custom` | `[{ id, title, aliases, type }]` | settings page, import | Hand-added works. Ids are `custom:<n>`. |
| `settings` | see contract | settings page, popup, shortcut | |
| `learned` | `{ names: { [id]: [name] }, not: { [id]: [key] } }` | content script ("Not this"), popup and settings page (names), import | Contract rule 11. Normalised by `cleanLearned` in `config.js` (names 2 to 60 characters trimmed, at most 20 per work, deduplicated ignoring case; keys `host` or `host/source`, lower-case) Unknown keys, such as the `clips` of an older file, are dropped (see [Remembered clips](#remembered-clips-not-shipped)). |
| `catalogIndex` | `{ builtAt, bin, meta, bundle }` | background | The rebuilt index: bundled catalog, works added by updates and hand-added works. `bin` is base64. `bundle` is the `builtAt` of the bundled catalog it was built against. Removed when there is nothing to add. |
| `catalogAdded` | array of works (catalog schema) | background | Works added by updates. Used to rebuild offline after an extension upgrade. |
| `catalogMeta` | `{ lastCheck, lastSuccess, lastError, added, found, stats: { queries, bytes } }` | background | Shown on the settings page. |

- `catalogIndex` is used only when `catalogIndex.bundle` equals the current bundle's `builtAt`. Otherwise the bundled index is used. `builtAt` is the modification time of `data/catalog.json` at build time (see [agents/pitfalls.md](agents/pitfalls.md)).
- Hand-added works are indexed with a popularity of 1,000 (`CUSTOM_POP`), so they are not treated as obscure works (an obscure name must be written in Title Case; written in lowercase it counts only as a weak "lowercase" name, and never when it is `common`, `ambiguous`, `other` or `rare`: decision rule 2). The background rebuilds `catalogIndex` whenever `custom` changes.
- Extra names (`learned.names`, contract rule 11) are appended, as given, to the `aliases` of their work before the index is built (`withNames` in `catalog-update.js`), for catalog and hand-added works alike, so the builder applies its alias rules with that work's own popularity and flags. The background rebuilds `catalogIndex` whenever `learned.names` changes (a change to `learned.not` alone does not rebuild), and the opt-in update and the rebuild after an extension upgrade include them. With no added works, no hand-added works and no extra names, `catalogIndex` is removed.
- **Migration from 0.1.** `seen` becomes `works` entries with `state: "seen"`, `settings.mode` becomes `settings.style`, and the old keys are removed. It runs when the background starts, when the extension is installed or updated, and again when a late 0.1-style write appears. Until then the content script reads the 0.1 keys as if they were 0.2.

## The matcher

`src/content/matcher.js` is plain JavaScript, loaded as a content script and also by Node. The Android build ports it to Java.

### Index

- A catalog key is a sequence of normalised tokens, up to 8 tokens. Longer keys are dropped.
- Each key is hashed to two 32-bit values. The table is one flat `Uint32Array` with open addressing, loaded as is. The file layout is `[magic, slotBits, format, ...slots]` and each slot is `hashA, hashB, value + 1`.
- Index format 3 is format 2 plus the type-narrowed names above (the key carries `\u0002` and the type; the value is the same). Index format 2 packs a value as `group << 9 | ocr << 8 | rare << 7 | cap << 6 | common << 5 | ambiguous << 4 | other << 3 | kind`. Format 1 (`group << 8`, no `ocr`) and format 0 (`group << 7`, no `rare`, `other` or `ocr`) still load, with the missing bits read as 0.
- Lookup costs about tokens x 8 hash probes. Memory per tab is about the file size. The shipped index is 1.6 MB (`index.bin`, 1,572,876 bytes, 77,633 keys, 80,941 entries with the type-narrowed names, of at most 81,920 before the table doubles) plus 2.0 MB (`index.json`, about 1.96 MB: it grew by about 30 KB with the series lists and by about 180 KB with the 0.2.4 catalog). Every frame of a page loads its own copy, so about 3.5 MB per frame.
- `index.json` holds per-work columns (`ids`, `titles`, `types`, `years`), sorted by popularity, `groups`: `[label, workIdx, workIdx, ...]`, and `series`: one list of work indices per catalog series with two or more works, oldest first (works with no year last), in order of each series' most popular work. `Matcher.moreFromSeries(groups)` returns the other works of the series that contain any work of the given groups, oldest first; the caller drops seen works.

A name maps to one group: the works it refers to (`closest` in `build-index.js`). The index builder records for each name which works carry it at which tier: 0 a title, 1 an alternative name (alias), 2 the series the name was derived from, 3 a character, 4 a part of a character's name. A bare name refers to its closest tier only. "Half-Life" is the 1998 game, not "Half-Life: Alyx". "Star Wars" is an alternative name of Episode IV and a derived series name, so it takes the works titled "Star Wars: ..." (films, games and shows). Franchise exception: the name also takes its series (tier 2) when the closest works are themselves entries of that series, or when the series' best work is at least 1.5 times as popular as the closest one ("Halo": a TV series titled "Halo" and the games "Halo 2", "Halo 3" and others). A type word right next to the name (before or after it, no sentence break between) narrows the group to the works of that type among the name's works: "the Minecraft movie", "Assassin's Creed game", "Assassin's Creed oyunu" (the type words are `TYPE_WORDS` in `matcher.js`, with English, Spanish, Portuguese, German, French, Italian and Turkish forms; "series" is not a type word). The narrowed group is stored in the index under the name plus `\u0002` and the type (index format 3), so a name next to a type word costs one more probe. A group is seen when any of its works is seen and none is blocked (contract rule 1). The odd results this produces are listed in the [README](../README.md#status-and-known-limits) ("Call of Duty" is only the 2003 game, "Pokémon" only the 1997 anime, "Harry Potter" the books and the 2026 series but not the films). `test/fixtures/franchises.json` holds the reviewed answers for 28 names.

### Tokens

- A token is a run of letters and digits. `&` becomes `and`. Text is lowercased. Non-ASCII text is decomposed and its diacritics removed.
- An apostrophe splits words. A short suffix after it (`'s`, `'t`, Turkish `'i` or `'nin`) is dropped when the word before it is longer than 2 letters, so "Interstellar's" and "Breaking Bad'i" keep their tokens. French `d'` and `l'` keep the word after them. The index also holds the apostrophe-less form ("Schindlers List").

### Kinds of name

| Kind | Example | Notes |
|---|---|---|
| title | "Breaking Bad" | |
| alias | "TLOU2", "gta6", "No Way Home" | Up to 8 per work. A single everyday word is never indexed as an alias; written in capitals it may be an acronym (next row). Since 0.2.3 a work's subtitle is an alias too, when no other name has its key: the last part of the title after `:`, an en dash or a hyphen, of 3 or more tokens or of 2 that are not both everyday words, carried by no other title ("Napoleonic Wars" of "Cossacks II: Napoleonic Wars"; not "Part Two" or "The Movie"). Its other senses were never looked up in Wikidata ("True Crime: New York City"), so a subtitle alias is always `other`. |
| acronym | "GTA", "GOT" | Kind 7. An alias written in the catalog in capitals only (2 or more letters, `ACRO` in `build-index.js`) that is a single everyday word in lowercase. Indexed only when people plausibly write it for that work (`usedAcronym` in `build-index.js`): the capitals are the initials of the title, of the title without a leading "The" or of its last part after a colon ("TOS", "CSI"), or the title spelled with stops ("W.I.T.C.H."); and the work has at least 45 sitelinks (`DISTINCT_POP`), or 60 (`COMMON_POP`) when the capitals spell one of the 10,000 most frequent words. "BIOS" (Finch), "PRO" (Star Trek: Prodigy), "ADVENT" and "BMW" (Black Myth: Wukong) are not indexed. With the 0.2.3 catalog ten are kept: GOT, SMB, ATLA, DBZ, MIB, CSI, TOS, GTA, ABA, TROP. Indexed only when no other name has the same key ("FRIENDS" stays the show Friends). It takes the group of the title of the work it belongs to, franchise rule included: "GTA" names what "Grand Theft Auto" names (the 1998 game and the numbered and subtitled games). When its works' titles name different groups ("SMB": Super Mario Bros. and Super Meat Boy), it keeps its own group, its works at tier 1 like an alias. Flags as for a single everyday-word alias: `cap` and `common`, never `ocr`. Rule 1 says where it matches. Kind 7 was the free value of the 3-bit kind field, so the format stays 3; an index built by an earlier version simply has no acronyms, and a catalog update on the device rebuilds the index with the shipped code. |
| series | "Star Wars", "Battlefield" | Prefix before `:`, an en dash or a hyphen, when at least two works share it. Also a name that is numbered in three or more titles ("Battlefield 3", "Battlefield 4", "Battlefield V"). Not derived from a single common word or fewer than 4 characters. The part after the colon (a subtitle) is indexed on its own only as a weak alias (row "alias"). Since 0.2.3 a subtitled title joins a series that is numbered elsewhere even when the prefix is one everyday word ("Halo: Reach" joins the series "Halo" of "Halo 2" and "Halo 3"). |
| character | "Walter White" | Full multi-word names (up to 8 per work). Real people are not fetched. |
| char1 | single-token character name | Weak. Must start with a capital letter. |
| part | "Snape" from a full name | Weakest. Must start with a capital letter. Parts that are everyday words are not indexed. |
| tag | `#BreakingBad` | Matches only when written with `#`. |

When one name plays several roles, the most title-like kind wins.

Flags on a name, set by the index builder:

| Flag | Meaning |
|---|---|
| `cap` | Must be written in Title Case (an otherwise strong title written in lowercase is a weak "lowercase" name, decision rule 2). Set for single-word names, names of works below 60 sitelinks and names made only of common words. |
| `common` | Made of everyday words and naming a less popular work (or a single everyday word at any popularity). Since 0.2.3 a name of two or more words is not `common` (and not `ambiguous`) when its combined popularity is 60 or more (`COMMON_POP`): the sitelinks of the works it titles, its alternative names, its derived series and its numbered or subtitled sequels ("Dark Souls II", "Dark Souls: Remastered") added up (`fame` in `build-index.js`). No single "Resident Evil", "God of War", "Dark Souls" or "Silent Hill" work reaches 60, so "Resident Evil is scary" used to match nothing. Two exceptions stay: "The" plus one word ("THE FALL OF CONSTANTINOPLE"), and a name with no later word of 3 or more letters. A bare number ("10.5", "1917") is `common` too: it needs a media word, quotes or a hashtag. "Everyday" means the first 1,000, 3,000 or 10,000 lines of `tools/catalog/common-words.txt` (the English 20k list, most frequent first) for the finer rules, and any line of it for the rest. Since 0.2.2 the file also holds subtitle words of six more languages (see [Catalog](#catalog)). |
| `rare` | A single uncommon word naming a work with fewer than 45 sitelinks (`DISTINCT_POP`; "Bloodborne"). Weak: it needs a media word in its sentence. From 45 sitelinks up such a word ("Minecraft", "Arcane") is not `rare`: it is a title however it is written. |
| `ambiguous` | The catalog's own flag: a title under 4 characters, one common word, or two top-1,000 words. |
| `other` | The name's dominant meaning in Wikidata is not a work (a place, a person, a brand, scripture). Set only when that holds for every work carrying the name. |
| `ocr` | Strong enough to count in text read from pictures. See [Text read from pictures](#text-read-from-pictures). |

### Decision rules

These are in `Matcher.evaluate`.

1. A tag needs the `#`. A char1 or part needs a capital first letter. An acronym must be written in capitals, 2 or more letters before any apostrophe suffix ("GTA", "GTA’yı"), and not in an ALL-CAPS run or on a Headline Case line (`caseless`, see "Case evidence"): "I GOT THE GAME YESTERDAY" and "got the game" do not name Game of Thrones. It is then a single everyday word (rule 6): "Playing GTA all night", "GTA is the best game series". Handles are not text: a name is ignored when it lies inside the run of `[\w.-]` characters after `@`, or after `u/` or `r/` whose `u` or `r` does not follow a letter or digit (X writes "Name@handle·3s" with no space before the `@`), and when its first token follows, or its last token is followed by, a `_` glued to a letter or digit ("u/Altruistic_Mud_8425", "@Mud_Lover99", "Altruistic_Mud_8425"; `HANDLE` in `matcher.js`). A hashtag is not a handle. The handle rule also applies to text read from pictures. A token inside a handle is no evidence either: "movies" in "r/movies" is no media word, type word or consumption verb ("u/Comic_Book_Reader r/movies Veteran • 20 hr. ago" does not name the film "Veteran").
2. A "cap" name must be written in Title Case ("The Walk", "Siberia"): its first token and every token longer than 3 characters that is not a function word (`STOP` in `matcher.js`: "with", "from", "about"...) must start with a capital letter or a digit ("Gone with the Wind"). A hashtag lifts this. Quotes do not. A cap name written otherwise is dropped, except a "lowercase" name: a title, alias or series that is not `common`, `ambiguous`, `other` or `rare`, not one token of 3 characters or fewer, not a bare number and not "the" plus one word ("resident evil 4", "breaking bad", "minecraft"). A `common` name of 3 or more tokens is a lowercase name too when a title, alias, series or acronym inside it (any index entry over fewer of its tokens) names a work of a catalog series that a work of its own group belongs to (`seriesInside` in `matcher.js`; the `series` lists of `index.json`, as `moreFromSeries` reads them): "dune part two" holds "dune", whose films are in the Dune series with "Dune: Part Two". It is weak and is accepted only by the evidence of rule 5 (another name of its group, quotes) or, in its own sentence, by a fitting media word within 3 tokens, the "is a ... game" pattern or a consumption verb right before it (rule 6). "day 3 of playing resident evil 4" matches; "Is this a resident evil oc" and "the boys were watching tv" do not. "dune part two was a great movie" matches "Dune: Part Two" and "just finished the last of us part 2" matches "The Last of Us Part II"; "the whole nine yards was a great movie" and "smiley face" stay unmatched (no name of the same series inside them).
3. The longest match wins, whether or not its group is seen. "Us" and "Last" inside "The Last of Us" are dropped. So is "Potter" inside "Harry Potter". A seen longer name still consumes the shorter name inside it. A name inside a lowercase name is not dropped but waits: lowercase names are judged first, longest first, and the names inside one are judged only when it is not accepted.
4. A match is weak when the name is `common`, `other` or `rare`, a char1 or part, a lowercase name, or a short or ambiguous title (ambiguous and at most 2 tokens, or one token of 3 characters or fewer), or when it is case-only (see "Case evidence" below). A strong match is accepted at once. So is a weak title, alias or series (not lowercase) that holds a strong title, alias or series of the text, which passed its own case test: the franchise name vouches for its entry ("Assassin's Creed Brotherhood", "Assassin’s Creed Shadows"), and the longer name stays the label.
5. A weak match is accepted without further tests when another, different name of the same group is in the text (not a lowercase name, and not a name inside it or holding it). It is also accepted when it is in a hashtag or in quotes (a comma or a full stop may come before the closing quote: '"Jailhouse Rock,"'), unless it is an `other` name or a part of a character's name: a hashtag or quotes are no evidence for "#Palestine" or a song title, and a part only corroborates ("H.M.S. ‘Beagle,’"). Since 0.2.3 a hashtag alone does not make a single word that is everyday, ambiguous or obscure a title ("#verity"); a distinctive tag still counts, and so do quotes. A name also counts when it lies inside the title of another matched name's work and shares no word with that name ("Fallout" and "New Vegas"; not "Castle" and "Castle Rock").
   Before that, two things drop a name whatever its strength (0.2.3, after the tuning posts' music and platform false positives). A name followed in its sentence by "stock", "stocks", "shares", "earnings" or "ipo" is the company ("Roblox stock jumped after earnings"). A name in quotes in a sentence next to a sentence about music (its own, the one before or the one after holding a `SONG` word: "album", "song", "track", "listen", "sings", "rendition", "lyrics", "verses", "gig", "jazz"... in `matcher.js`) is a song, unless its own sentence has a media word of its type: 'If you only know "Hound Dog" and "Jailhouse Rock," go listen to Elvis's gospel albums', '"Simple Twist of Fate" is perfect' after a sentence about an album. There quotes are no evidence either.
6. Anything else needs a capitalised first letter, and a part name stops here. What follows looks only inside the name's own sentence (a sentence ends at `.`, `!`, `?` or a line break, except after an ordinal like "2."). A media word must fit the work's type: "game" corroborates a game, not a film, and "Nintendo Switch" says nothing about a film called "Switch". The words are in the `CONTEXT` table of `matcher.js`: English, plus Turkish (with suffix stems), Spanish, Portuguese, German, French and Italian.
   - A Title-Case name (`titleCase` in `matcher.js`: its first word and every word that is not a function word capitalised, two of them of 3 or more letters) is accepted when it has 3 or more tokens, or 2 tokens followed by a possessive or a copula ("is", "was"...), as long as it is a title, alias or series, not `other`, not a lowercase name, not two top-1,000 words (`ambiguous`), not "The" plus one word, not in a caseless run or line (see "Case evidence") and not next to a sentence about music. "Horizon Zero Dawn's first Thunderjaw fight", "Your Lie in April made me cry", "Fall Guys is silly joy", "Tears of the Kingdom's Ultrahand". It must not be part of a longer name or a list of names: no capitalised word right before it (skipping "of", "and", "the"; the first word of the sentence does not count) or right after it (a copula, or anything after a possessive, does not count), and not followed by "of" and a capitalised word. "Royal Air Force's", "Department of Parks and Recreation", "Marine Corps, and Coast Guard are", "the Old and New Worlds", "On the Origin of Species" do not match. Two-word names mid-sentence with no possessive or copula are left out: on `tools/fp-text.mjs` they matched "General Hospital", "Coast Guard", "Country Girl" and more than they found. The remaining cost there is real Title-Case institutions and phrases that are also titles or aliases ("Leave No Trace", "North-West Mounted Police", "Mobile Army Surgical Hospital"): 9 more flagged sentences of 24,535.
   - Next to a sentence about music (as above), a weak name takes only a media word right next to it or a release year ("Local music scene in Brooklyn this week: a free jazz night..., a punk gig in a converted garage in Bushwick" does not name the film "Bushwick" through that "scene").
   - Next to a sentence about sport (`SPORT` in `matcher.js`: "stadium", "league", "coach", "tournament", "derby", "nba"...), season and game words ("season", "saison", "temporada", "game", "jeu", "jogo", Turkish "sezon" and "oyun" stems: `SPORTY`) are no evidence: "...au Groupama Stadium... Belle saison en vue pour Lyon" does not name "Belle".
   - An `other` name takes only a fitting media word within 3 tokens. If it is also an everyday word at the start of a sentence, only a media word right next to it.
   - Otherwise a release year of one of its works in the same sentence is enough.
   - A name of two or more tokens, none longer than 3 characters ("Q & A", "Get Out"), takes only that year or a fitting media word within 3 tokens: "Want to promote your film via community AMA/Q&A?" does not name the film "Q & A"; "the film Q & A" and "Q&A (1990)" do.
   - An everyday-word name at the start of a sentence needs a second capitalised word of 3 or more letters ("The Bear", not "Marley and Me"), or else a media word right next to it. After a possessive "right next to it" reaches one word further ("Succession's final season"). A suffix after an apostrophe that is not English ("'s", "'t", "'ll", "'re", "'ve", "'d", "'m") counts as the capital: Turkish writes one only after a proper name ("Succession'ı baştan sona bitirdim").
   - A single everyday word takes a fitting media word within 3 tokens.
   - Other weak names take a fitting media word anywhere in their sentence. One that is neither `common` nor `ambiguous` and starts its sentence also takes one from the sentence before or after it, but only a word of some work types, not one that fits every type ("characters", "series", "ending") and not a weak one (`YT`, "scene"): "Deltarune chapter 2 had me grinning. Toby Fox gave us the best boss fight of the year." On 3-sentence windows of the `tools/fp-text.mjs` corpus this added no flagged window (it added two before the type-word restriction: "characters", "scene"); "Severance pay is due in March. We binged a show on the weekend." stays unmatched ("Severance" is `ambiguous`).
   - A case-only match (below) takes only a media word right next to it, or a type word of its works within the next 3 words of its sentence ("Until Dawn | FULL HORROR GAME": 0.2.3; a name whose capitals prove nothing and that is not already accepted otherwise).
   - A bare number never matches a numeric title on its own: it needs quotes or another name of its work (".45" against YouTube's spoken "45 minutes"; 0.2.3). A hashtag does not lift it.
   - In a line that already names a work, a single everyday word takes only a media word joined to it by a space (before or after it), a type word, or a sentence that says what it is ('Coco is a gorgeous film about family. "Remember Me" at the end.'). The matcher judges the names that are not everyday words first, and a line is "named" by an accepted one. "DmC: Devil May Cry - All Boss Fights & Ending (No Damage" no longer adds the films "No" and "Damage" (0.2.3; a line is ended by a line break or the OCR marker; `test/catalog.test.js` has the DmC case).
   - A single-word name that is a determiner, quantifier or pronoun (`DET` and `SUBJECT` in `matcher.js`, plus no, any, all, some, more, most, every, each, both, another, other, these, those) takes nothing from the media word right after it (after a number between, too), in any of the tests above: "No spoilers please!" and "8 No Spoilers" do not name the film "No"; "Watched the film No last night" does.
   - Music titles: when the post's own text has "ft.", "feat.", "prod.", "official (music) video" or "audio", "music video", "lyric video", "(lyrics)" or Turkish "klip" (`MUSIC` in `matcher.js`), a single-word name matches only with quotes, a distinctive hashtag or another name of the same work. "Joker ft. Defkhan, Kurşun - Son Kale | official video" is a song, not the film "Joker" (0.2.3). Since 0.2.4 the same holds when the own text has a music word, `album(s)`, `freestyle`, `remix(es)`, `mixtape`, `diss track`, or Turkish `albüm`, `şarkı`, `konser` with any suffix (`MUSIC_WORDS`), and no media word at all: "Joker yeni albüm çıkardı" and "Joker freestyle" name nothing, "Joker soundtrack album, haunting" still names the film (`soundtrack` and `ost` are media words). "live in <place>" is not a music word: it is everyday English.
   - The uploader's name (contract rule 9; 0.2.4). Text after U+0002 and before any U+0001 is the uploader (a YouTube channel). It is replaced by a line break and spaces before the scan, so it is no name and no evidence, and every offset stays put. Its key is its tokens minus a trailing `official`, `vevo`, `music`, `muzik` or `topic` (also glued to the last token: "JokerVEVO"; never the only token; `uploaderKey` in `matcher.js`). A name of the own text with that key is weak and takes no shortcut: not strong, not quotes, a hashtag, another name of its work, a longer name holding it or Title Case. It is accepted only by a fitting media word within 3 tokens in its sentence, the "is a ... game" pattern or a consumption verb before it, a type word of its works within the next 3 words, or a release year of its works in the sentence. It is never unsure, and it vouches for no other name. "Joker - Mikrofon Şov", "Element - Joker", "Joker & Allame - Rapstar", "JOKER - ŞİFA" from the channel "Joker" name nothing; "Joker (2019) ending explained", "Joker review" and "Minecraft - Official Trailer" from the channel of the same name still match. Lost: a clean title with no media word from a channel named like the work ("Minecraft" from "Minecraft").
7. A group whose works are all inside another matched group adds nothing.
8. The result is ordered by label tier: groups the post's own text names first, then groups named only by OCR text; within a tier the group matched by the longer name first, then the more popular work (the index sorts groups by popularity). Seen groups are dropped, and when the own text names only seen works the OCR-only groups are dropped too.

Names these rules neither accept nor drop are returned by `Matcher.unsure` as [unsure names](#unsure-names) for the title-in-context model; the contract's "Names the matcher is unsure about" has the rule, and an accepted name from the model is decided like any other group.

Media words: `series`, `serie`, `serien` and the Turkish `serisi`, `serinin` and `seriye` count for every work type, as do `antihero` and the Turkish stem `bitir` ("bitirdim": I finished). Since 0.2.3 also `anthology` (screen and reading), `simulator` (games) and `memoir` (reading); the Portuguese consumption verbs `terminei` (any type) and `zerei` (games) count right before the name. `scene` and `scenes` do not count right after a single everyday word, with which they make a compound ("Music scene in Lagos", a `NOUN` bit). Left out on purpose: `runtime` (software), `sequence` (maths, DNA), `strip` ("Gaza Strip"), `noir` (French for black), `port`. Video-title words are weak media words (a `YT` bit in `CONTEXT`): `review`, `reaction`, `soundtrack`, `ost`, `lore`, `recap`, `breakdown`, `masterpiece`, `remastered`, Turkish `inceleme`, and for games `walkthrough` and `mods`. A name flagged `common` never takes them ("Switch 2 Review" does not cover a film called "Switch"). `actor`, `actress` and `acting` are not media words any more.

### Case evidence

In an ALL-CAPS run of two or more words, or on a Headline Case line (at least 4 words of 4 or more letters, 70 percent of them capitalised: "Grace Ashcroft's Voice Actress Reacts to Thirst Comments"), capital letters prove nothing (`caseless` in `matcher.js`; the post's own text only). There a name that relies on case needs a media word right next to it. That is a Title-Case name that is a single word or two everyday words and that is `common`, ambiguous, `rare` or `other`: "KES", "Thirst", "The Master". So is any single word joined there by "&" to another word, one of a pair of names: "KHONTKAR & JOKER YAYINI" (two performers) does not name the film "Joker"; a pair that is itself a title ("BATMAN & ROBIN") is a longer name and wins. A distinctive single word does not rely on case: a word that is not an everyday word in any shipped list, not `other`, naming a work with at least 45 sitelinks ("Minecraft", "Arcane") is a title however it is written, in a headline or in capitals.

### Text read from pictures

The caller passes OCR text after the post's own text behind one U+0001 character (contract, rule 8). The matcher treats the part after the marker like this:

- A name counts only if the index marks it `ocr` (strong). The builder sets that bit for a title, alias or multi-word character name written as it is in the catalog (not a sequel-number swap or a joined form such as "gta6"), with at least two tokens, that is not `other`, and one of: at least two real words (3 or more letters, not `the`, `and` and the like; for a less popular work the name must also not be ambiguous); one real word that is not an everyday word in a name of a work with at least 60 sitelinks (`COMMON_POP`; "The Mandalorian" has 55, so "THE MANDALORIAN" does not match from picture text); or a sequel-numbered title with a word of 4 or more letters outside the 3,000 most frequent ("BATTLEFIELD 4"; "GEN 5" exists only as the swapped form of "Gen V" and does not count).
- Never a single word: a thumbnail that only says MINECRAFT matches nothing. Case, quotes and hashtags are not looked at.
- A name never crosses the marker, and a sentence ends at it, so a media word in OCR text does not corroborate a name in the post's own text, and a media word in the own text does not confirm an OCR name. OCR text never corroborates a weak own-text name through another name of the same group either.
- When the own text names only seen works, OCR-only groups do not cover (contract, rule 7).

Why so strict: thumbnail text is all capitals, full of logos, timers and shouty phrases, so a single OCR word is nearly always noise. The figures are in the README (`tools/fp-ocr.mjs`).

### Sequel numbers

At build time, names with Roman or Arabic sequel numbers from 2 to 20 are written both ways ("Grand Theft Auto VI" and "grand theft auto 6"). For two-token names the joined forms are also indexed ("gta6", "gtavi"). "I" is never a numeral, and a numeral only counts after another word. A numbered name of a popular work, or a non-everyday short word plus a number, may match in any case. "Chapter 6" and "Windows 11" still need corroboration.

### Unsure names

Since 0.2.4 the matcher also returns the names it is unsure about (contract, "Names the matcher is unsure about"), for the title-in-context model. `evaluate(text, groupSeen)` returns what it returned before and keeps the unsure names of that scan. `unsure(text, groupSeen)` returns them as `[{ g, s, e, o }]` (group, character offsets in `text`, and `o` = 1 when the index flags the name `other`: it mostly means a person, place or brand, and the caller asks the model with a stricter threshold), reusing the last `evaluate` of the same text and the same `groupSeen` function, or scanning once itself. Java: `Matcher.unsure(text, seenWork)` returns `int[][]` of `{g, s, e, o}`, and `evaluate(text, seenWork, list)` fills a list in the same scan.

- Candidates: every title, alias, series or acronym of the post's own text (before the OCR marker) that the rules did not accept. That includes the names rule 1 or 2 drops before judging them: an acronym not in capitals or in a caseless run, and a `cap` name typed in lowercase that is `common`, `ambiguous`, `other`, `rare`, or short ("lost was peak tv").
- Never unsure: the uploader's name (contract rule 9), names in OCR text, in a handle or glued by "_" (rule 1), characters, parts and tags, a lowercase single-word determiner, quantifier or pronoun ("it", "her", "no"), a bare number, a group the rules accepted (own text or OCR), a seen group, and a group whose works are all inside an accepted group. Songs: a quoted name that rule 5 drops as a song (next to a sentence about music), with the names inside it, and every name of a post whose own text the `MUSIC` pattern marks as a song title ("ft.", "official video"...). A lowercase single word when the post's own text has a letter outside ASCII (ı, ş, ö, é, ã, ñ, ß...): the model is English-only and cannot tell a Turkish or Portuguese everyday word ("heat dalgası": heat wave) from a title. Capitalised and multi-word names stay unsure there. This is a shortcut: a non-English post written without diacritics is not caught; it goes when the model is multilingual. A name typed all in lowercase (no capital letter in it as written), when the post's own text (before U+0002 and U+0001) has no English function word as a whole token outside the name's own tokens: `EN_WORDS` in `matcher.js` (Java: `Matcher.EN_WORDS`, the same 66 words). The list leaves out words that are frequent in Turkish, German, Spanish, French, Italian, Portuguese or Dutch written without accents ("a", "i", "in", "on", "so", "her", "can"), except "is" and "was", without which short English posts ("lost was peak tv") lose their name. It catches non-English text typed in ASCII ("Gezinmeyi atla", YouTube's Turkish "Skip navigation", once asked as "ATLA"; "road trip çok güzeldi"). A name with a capital is not held to it: video titles often have no function word ("Halo Lore Stanley Plays"), and applied to every name the rule cost 13 of 250 `headlines.jsonl` rows. Measured on 2026-11-20 with `tools/eval-context.mjs` (tuned-on development sets), rules-or-model recall and everyday rows covered are the same as without the rule: `fp-posts.jsonl` 296 of 312 and 4 of 651, `headlines.jsonl` 227 of 250 and 10 of 250, `posts-dev.jsonl` 162 of 200 and 0 of 200.
- Volume guard: never a single word that is one of the 1,000 most frequent words of `common-words.txt`, or an everyday word (any line of it) whose works have fewer than 45 sitelinks (`DISTINCT_POP`); never a name of more words that is `common` (everyday words, a less popular work: "the way", "last night"), unless the index marks it `ocr` (two real words, strong enough for picture text: "road trip", "match point", "collateral damage"). The index builder writes the single-word guard into the `ocr` bit, which a one-word name never has otherwise; the matcher reads that bit as `ocr` only for names of two or more tokens. The format stays 3. "heat", "lost", "dark", "split" are asked; "it", "home", "species", "police" are not. "i lost my keys again" asks about Lost (the model says no).
- A name overlapping an accepted name of the own text is not asked ("Dune" in "Dune: Part Two"). Among overlapping unsure names the longest wins, then the earlier. One name per group, the first in the text; at most 4, in group order (most popular first).

Measured before the lowercase function-word rule (added 2026-11-20) and not re-measured since (the guard was chosen on these, so they are tuned-on figures; `tools/eval-context.mjs` on 2026-11-20 gives 0.36 unsure names per everyday row of `fp-posts.jsonl` and 0.37 of `headlines.jsonl`): unsure names per post, before the cap of 4. `test/fixtures/fp-posts.jsonl` non-media rows: 0.369 on average, 95th percentile 2, at most 3 (191 of 651 posts have one; 77 of the names are `other`). `headlines.jsonl` non-media rows: 0.368, 95th percentile 1, at most 3 (19 `other`). The `tools/fp-text.mjs` corpus: 0.125 per sentence, 95th percentile 1, at most 5 (2,789 of 24,535 sentences; 595 `other` names). With the top-1,000 cut alone it was 1.88, 1.04 and 0.86; with every multi-word `common` name silent, 0.30, 0.34 and 0.115. The ceiling for the model, media rows with the expected work accepted or among the unsure names: fp-posts 306 of 312 (305 after the cap; 281 accepted today), headlines 228 of 250 (228 after the cap; 180 accepted).

### Known limits

- Some bare franchise names refer to a single work or to no work ("Call of Duty", "Terminator"); see the README.
- A single-word title at the start of a sentence, with no media word in that sentence (or, for a word that is no everyday word, in the sentence before or after), goes unmatched.
- Characters corroborate only when the catalog has them: Wikidata gives none for "Succession", "Blue Lock" or "Haikyu!!", so "Kendall", "Isagi" or "Hinata" say nothing.
- An everyday-word title with no media word near it ("Dune Was Incredible", "Why Lost Failed") is not accepted by the rules. It is an [unsure name](#unsure-names), and the title-in-context model decides it; the model gets some wrong in both directions, and its training text is mostly English.
- A single word in picture text goes unmatched.
- Everyday words that are in none of the word lists (Vertigo, Scrubs) count as distinctive: "I bought new Scrubs for work" is matched to the series.
- A few non-fiction names still match.

## Styles

A work's effective style is its own `style`, or `settings.style` when it has none. The contract has the full rule. In short:

| Style | Text-only match | Image-only match |
|---|---|---|
| `all` (default) | Covered at once: "Mentions {t}". | Covered. |
| `spoilers` | Covered while the classifier runs ("Checking {t} for spoilers…"), then kept only if it says spoiler. Covered if the classifier fails. | Covered ("Image from {t}"), whatever the style. |

In `spoilers` style a bare title mention is shown once the classifier clears it, so a trailer title is not hidden.

### The classifier

- Model: `sentence-transformers/all-MiniLM-L6-v2`, fine-tuned end to end with mean pooling and one linear output. Int8 ONNX, about 23 MB (`models/spoiler/model_int8.onnx`).
- The text is split into sentences (`.`, `!`, `?`, newlines). At most 16 sentences are scored. `@handles` are removed. Sentences of 3 characters or fewer are skipped.
- Each sentence is scored alone (64 tokens max), because the int8 model quantises activations per tensor and batching would shift the scores. The post's score is the highest sentence score. A single spoiler sentence is not diluted by the rest.
- The post is a spoiler when `sigmoid(max logit) >= threshold`. The threshold is in `models/spoiler/meta.json` (0.8). It was chosen by balanced accuracy on validation data (held-out patterns, a split of the hand-written sentences, and `test/fixtures/spoiler-val.jsonl`), not on an evaluation set.
- Training data (`tools/train-spoiler.mjs`): hand-written sentences, hand-written patterns filled with catalog titles, hand-written look-alike non-spoilers (death and betrayal words about real life, players and viewers, premises, production talk), Reddit comments (CC BY-SA 3.0) and English Wikipedia sentences of 300 popular works (CC BY-SA 4.0): late plot sentences as spoilers, premise, production and reception sentences as non-spoilers. Since 0.2.3 also `tools/spoiler-train/gaps.mjs`: implied spoilers without "dies", "ending" or "twist", spoilers and look-alikes in Turkish, Spanish, Portuguese, German and French (the tokenizer is the English one, so these languages are only learnt through word pieces), video titles, real deaths, guesses and everyday uses of spoiler words.
- Cost: about 12 ms per sentence in Node with one thread (the image work's figure). `tools/eval-spoiler.mjs` printed 14 ms per post on one run and 39 ms on another with the machine busy.
- Classification has the highest queue priority, ahead of images.

### Title in context model

- Decides the [unsure names](#unsure-names): does this name, in this post, mean the work? Same family, tokenizer and runtime as the spoiler classifier (`models/context`, int8 ONNX, about 23 MB), trained by `tools/train-context.mjs` ([development.md](development.md#title-in-context-model)). It applies in both styles; a yes is an ordinary text match, so in style `spoilers` the post then goes to the spoiler classifier.
- Input (`src/shared/context-input.js`, the one copy: the content script, the engine and `tools/context-train/window.mjs` use it): segment A is the post's own text cut to about 100 characters on each side of the name, which is marked as `<name>`; segment B is `{group label} [{types}]`. The engine tokenises both without special tokens and assembles `[CLS] A [SEP] B [SEP]` with token types itself (`pairIds`), cutting A from its end to fit `maxLength` (128), exactly as `tools/context-train/classify.mjs` does (`test/context-input.test.js` checks it, and the e2e test checks the engine's probability against the Node runner's).
- One pair per run, no padding. Loaded on the first question, beside the spoiler classifier, with the same thread settings. The threshold (and `thresholdOther` when present; otherwise the one threshold serves both kinds of name) is read from `meta.json` at load.
- A failed or missing answer is a no (fail open), unlike the spoiler classifier: these posts were never covered before 0.2.4. Questions share the classifier's queue priority, ahead of images.

Results are in the [README](../README.md#status-and-known-limits). `all-MiniLM-L12-v2` was tried as the base and was no better on validation, slower and larger. The AUC on `spoiler-eval.jsonl` was likely optimistic in 0.1 because the training patterns resembled its "implied" posts; `spoiler-eval2.jsonl` was added as a second check, with the caveat given in the README.

## Images and video

Media scanning is controlled by `settings.scanImages`. Until an image has a verdict it is drawn as a dark placeholder (`filter` in `content.css`).

### Content script side

- Images, videos and inline-style background photos are queued for scanning when they come within one viewport height of the screen (`IntersectionObserver`, `rootMargin: 100% 0px`).
- An image is skipped when either side is under 96 px (natural size or displayed size). Only `http(s)`, `data` and `blob` sources are scanned.
- Readable images (same-origin, CORS, blob) are redrawn to a canvas of at most 768 px on the long side and sent as a JPEG data URL. Cross-origin images and CSS backgrounds are sent as a URL, and the background fetches them with the extension's host permission and without credentials.
- Both verdicts are required before the image is revealed: title check and OCR. An engine error or a 60 second silence (a safety net for a lost message) reveals the image and is counted in `data-sb-stats`.
- Video: the `poster` is scanned. During playback a frame (at most 448 px) is scanned at most every 5 seconds. If a frame turns out covered, the video is paused. A video stays a placeholder until its first frame has a verdict. Videos from other origins without CORS cannot be sampled, so only the poster and the surrounding text count.
- OCR text is added to the block's text after the post's own text, behind one U+0001 character, and the matcher runs again (see [Text read from pictures](#text-read-from-pictures)). A title verdict of a group or "unknown" is kept per picture. `mediaInfo` drops a picture's model title when that picture's own OCR text names a work (rule 7); `decide` drops all model titles when the post's own text names one.

### Engine side

Requests go through one priority queue, lowest number first. Order: classifier (-1), in-viewport title check (0), its OCR (1), off-screen title check (2), its OCR (3). Title checks waiting at the same priority run as one batch of up to 4, which shares the cost of restoring the weights on every run. Downloaded images are kept in a small cache (24 entries) so OCR reuses the title check's download. Title verdicts are cached (2,000 entries).

**Title verdict** (`verdict` in `engine.js`):

1. The whole image is squashed to 256 x 256 (no crop) and normalised with mean 0.5 and standard deviation 0.5. The resize is done in plain JavaScript (`squashCHW` in `src/background/pixels.js`, a triangle filter like PIL's antialiased bilinear, which SigLIP's own processor uses) on the decoded pixels, not by the canvas: the canvas scaling filters of Chrome and Firefox differ. With the canvas the score of an image differed between browsers by up to 0.010; with `pixels.js` by at most 0.0013 (median 0). A run on one browser is bit-identical, and a batch of 4 gives the same scores as single images. `tools/calibrate-clip.mjs`, Android (`Images.visionPixels`) and the tests use the same computation. (Images over 2048 px are first scaled down by the canvas.)
2. Run the SigLIP 2 base/32 vision tower and take `pooler_output`, normalised.
3. Compute `neg`: the best cosine to the 33 generic prompts ("a photo", "a selfie", "a meal on a plate" and so on).
4. Score the image against the title matrix (2,000 rows, int8). Each row is the normalised mean of 3 prompts for the work's type ("the poster of the movie {t}" and so on) and, for works that have them, 2 character prompts ("{c} from {t}").
5. A row names a title when its score is at least `minScore`, beats `neg` by `margin`, and beats the best row of an unrelated title family by `titleGap`. A family is the rows whose groups share a work, so the "Star Wars" row and the "Episode IV" row count as one. The result is up to 3 groups of that family that also clear the margin.
6. Otherwise, if the best of the 20 media prompts ("a movie poster", "a scene from a TV series" and so on) beats `neg` by `mediaGate`, the result is group `-1`: media with no certain title. It covers only when `settings.unknownImages` is on, and it is never offered as "I've seen it".

Cut-offs, set in `tools/build.mjs` (`CUT`) and stored in `data/clip-meta.json` with the preprocessing constants:

| Name | Value |
|---|---|
| `minScore` | 0.1355 |
| `margin` | 0.077 |
| `titleGap` | 0.015 |
| `mediaGate` | 0.0516 |
| rows (`--clip-n`) | 2000 |

They come from `tools/calibrate-clip.mjs`, which fits them on all calibration images and reports a two-fold split (media images split by work, ordinary photos by file name) so that the reported result is held out. The held-out total is in the README. The shipped values are fitted on all images including the fixtures, so the fixture figures are not held out. They were recalibrated after the merged catalog and the `pixels.js` resize landed. The calibration is noisy: the two folds pick very different cut-offs (for example `titleGap` 0 on one and 0.0325 on the other), so a small change in the data moves the held-out result by a few images.

The title tower's weights are quantised to int8 and the activations stay fp32. Ordinary int8 quantisation of activations breaks this model (see [agents/pitfalls.md](agents/pitfalls.md)). `tools/quantize-vision.mjs` does it at build time, without Python, from a pinned fp32 download. Restoring the weights on every run costs time, so since 0.2.1 the engine folds them to fp32 once at load (`disable_quant_qdq` in `engine.js`). The scores are identical (same weights; `tools/bench-stats-diff.mjs` shows a spread of 0 on the 87 fixture images in both browsers). One image alone went from 403 to 175 ms in Chrome and from 629 to 448 ms in Zen; the Chrome extension process went from 481 to 991 MB. Remove the setting to trade the speed back for memory.

Works added by a catalog update or by hand have no title rows, so their images only get the generic verdict.

**OCR** (`src/background/ocr.js`): PaddleOCR v5 mobile, a detector and an English recogniser, as ONNX files from RapidOCR, on onnxruntime-web. Steps:

1. The image is scaled to at most 1280 px on the long side, then to a detector input with the long side at most 960 and the short side at least 384 (small thumbnails are upscaled), in multiples of 32.
2. The detector's probability map is thresholded at 0.3. Each connected component with at least 4 px on its short side and a mean probability of at least 0.6 becomes an axis-aligned box, grown by the DB "unclip" ratio of 1.6.
3. Each box is cut out, scaled to 48 px high (at most 960 wide) and recognised. A line counts when the mean character probability is at least 0.6.
4. Lines are sorted into rows and read top to bottom, left to right.

There is no worker and no time limit in the engine. Rotated text reads worse because the boxes are not rotated (a `shortcut` comment in `ocr.js`). The output goes to the same text matcher as any other text.

### Remembered clips (not shipped)

Contract rule 11's third report, `Remember the video on this page`, is not in the extension. It was measured first, with `research/scripts/refframes/clipmatch.mjs` on the cached embeddings of about 5,000 frames from 60 videos (`research/data/refframes/`, the product's vision tower and preprocessing; not in git). A remembered clip was modelled as 12 frames one every 5 s, stored as int8 like the title rows; a re-post as the frames between them (2.5 s off at 0.4 fps). Videos were split in two halves by a hash of the id; the threshold was the lowest with no match between different videos on one half and was reported on the other.

| int8 stored frames | `clipMatch` | Frame pairs | Query frames | 30 s windows (6 samples) | Different-video matches |
|---|---|---|---|---|---|
| fit on half 0, held-out half 1 | 0.9905 | 0.4% | 2.7% | 8.8% | 0 of 4,312 |
| fit on half 1, held-out half 0 | 0.9881 | 0.3% | 2.5% | 9.6% | 1 of 4,530 (same game) |
| fitted on all 60 videos | 0.9972 | 0.1% | 0.8% | 3.3% | 0 of 17,995 |
| (looser, for scale) | 0.95 | 4.6% | 26.3% | 64.1% | 36 of 17,995, all within one game |

The highest different-video cosines are between videos that share footage (GTA VI trailers 1 and 2 and the launch trailer, GTA V's gameplay video and trailer, two clips of the same film), so "no match between different videos" forces the threshold to about 0.99, where a frame 2.5 s away from a stored one is rarely recognised. That is far below the bar set for shipping (30% of frame pairs or about 60% of 30 s windows), so no popup button, engine change or `clipMatch` exists.

## Catalog

### Format

`data/catalog.json` is `{ "version": 1, "series": {...}, "works": [...] }`, sorted by popularity (Wikidata sitelink count), highest first. Each work:

| Field | Meaning |
|---|---|
| `id` | Wikidata QID. |
| `title` | English label (or the `mul` label). |
| `type` | `movie`, `tv`, `game`, `book`, `anime`, `manga` or `comic`. |
| `year` | Earliest date of the work, or `null`. |
| `aliases` | Up to 10 alternative names, at least 3 characters: up to 8 English (or `mul`) labels, then the main title of a subtitled title and one name in another language (see below). |
| `characters` | Up to 8 character names of two or more words, not real people. Only for works with at least 40 sitelinks. |
| `pop` | Sitelink count. |
| `ambiguous` | True for a title under 4 characters, one common word, or two top-1,000 words. |
| `other` | Optional. The title, aliases, characters or series prefix of this work whose dominant sense in Wikidata is not a work. |
| `series` | Optional (0.2.3). Ids of the series or franchises the work belongs to, keys of the top-level `series` table. |

The top-level `series` table maps a series id (a Wikidata QID) to `[label, ...the Wikidata series ids rolled up into it]`; it has 1,598 entries. The shipped catalog has 26,968 works (14,956 films, 4,143 books, 2,928 games, 2,814 series, 1,014 manga, 852 anime, 261 comics; counted in `data/catalog.json`). 3,034 of them have an `other` list. The 0.2.3 catalog had 24,609 (2,876 books, 465 manga, 424 anime, 146 comics, 2,862 with an `other` list); the 0.2.0 catalog had 24,670. When a work fits several types, the first of anime, tv, movie, game, manga, comic, book wins. The film series class is excluded.

Works need at least 15 sitelinks, except (since 0.2.4) anime, manga and comics, which need 10, and books, which need 12 (`LOW_MIN` in `tools/catalog/build.mjs`). Those have fewer Wikipedia articles than films and games of the same fame: "Circe" (Madeline Miller) has 12, the comic "Saga" 14, the "Code Geass" anime 14. Books stop at 12 because of the index size: the hash table of `index.bin` has 131,072 slots for at most 81,920 entries (load factor 1.6 in `buildIndexBinary`), and one more entry doubles the file to 3.1 MB. With the 0.2.4 catalog it holds 80,941 entries; going down to 10 for books as well would add about 3,300 more. So "Piranesi" (10 sitelinks) and "Tutunamayanlar" (5) are still not in the catalog.

Also since 0.2.4:

- A media franchise item (P31 Q196600) with at least 15 sitelinks and an anime or manga among its works stands in for them, as an anime (when one of its works is an anime) or a manga. Some anime have their Wikipedia articles on the franchise item: "One-Punch Man" (48 sitelinks; its anime item has none). It is dropped when its name is already a title, alias or series prefix of a catalog work, or when one of its works in the catalog is of another type (a film or game franchise with a side anime). 26 are kept (One-Punch Man, Trigun, Dr. Slump, Slayers, Love Live! School Idol Project, Tenchi Muyo!...).
- A graphic novel is told as a story even when it is a memoir or a biography (`NARRATIVE` has Q725377): "Maus" and "Persepolis".
- The main title of a subtitled title is an alias when no other work carries it as a title, alias or series prefix and it is no character's name or part of one: "Rogue One", "Death Stranding 2", "Bloodstained" (497 works). A single uncommon word of a work below 45 sitelinks stays `rare` in the index, so it needs a media word.
- A work with at least 60 sitelinks gets one name in Turkish, Spanish, Portuguese, German, French or Italian (Wikidata labels first, then other names; the one given most often): "Der Pate", "El rey león", "Yüzüklerin Efendisi: Kralın Dönüşü" (624 works). Left out: single words (an everyday word of some language or a person's name: "Yedi" for "Seven", "Fausto" for "Faust"), names the work already has, two very frequent words, and names that hold the English title (which matches there already). These names were looked up in the `other` step like the others, but only against English and `mul` labels. Works below 60 sitelinks get none, for the index size ("El Chavo del Ocho" of "El Chavo del 8", 52, "Duna: Parte Dois" of "Dune: Part Two", 58). The catalog update fetches no such names for new works.

The catalog keeps works that are told as a story. A work is dropped when its instance-of, genre or form (P31, P136, P7937) is on an explicit list of scripture, reference works, non-fiction, documentaries, news and talk shows (`NOT_NARRATIVE` in `src/shared/catalog-rules.js`), unless it is also a novel, short story, play, fiction, a fiction film genre or (since 0.2.4) a graphic novel. This dropped 797 works from the 0.1 catalog. Since 0.2.2 the list also holds contests (music competitions), award ceremonies, game and quiz shows, variety and sketch shows, albums and music videos, which removed 61 more works (38 films and 23 series, net: the count went from 24,670 to 24,609). Reality competitions and talent shows are kept on purpose, because their results are spoilers (`NARRATIVE` lets them through). A work of such a class that is left out is also a sense of its own in the `other` lookup, so a name shared with it can be `other`.

`other` is computed by looking up each name (title, aliases, characters, series prefix) on Wikidata: an item with the same English or `mul` label or alias, more sitelinks than the work, and a class that is not a work, a franchise, a character or a disambiguation page. `tools/catalog/common-words.txt` is the common-word list behind `ambiguous` and the index rules. `tools/catalog/words.mjs` builds it: the English list `20k.txt` (most frequent first; the index rules use its first 1,000, 3,000 and 10,000 lines), then the 5,000 most frequent subtitle words of each of English, Turkish, Spanish, Portuguese, German, French and Italian from `hermitdave/FrequencyWords` (OpenSubtitles 2018, CC BY-SA 4.0), so a title that is an everyday word in one of those languages ("Kes", "Thirst") counts as one in text of any language. The result has 42,041 lines. The script downloads the lists once into `tools/catalog/cache/`. It is a build input of the catalog (`ambiguous`), the index and the extension, which copies it to `data/common-words.txt`.

`npm run build` compiles the catalog into `index.bin` and `index.json`, the title matrix, and copies the pieces the update needs (`catalog.json`, `common-words.txt`, `catalog-classes.json`, `catalog-info.json`). `catalog-classes.json` also has a `sameSense` list: the classes that count as "a work or a fictional thing" for the `other` lookup.

### Series membership

Names and series are two things. The matcher's name groups come from titles (above). The catalog's `series` field says which works belong together, for the picker's "More from this series" section (contract). `tools/catalog/series.mjs` builds it as step 6 of `tools/catalog/build.mjs`, after the `other` lookup:

1. Each work's Wikidata "part of the series" (P179) and "media franchise" (P8345) statements are fetched. Only items whose class is a series or franchise count (`SERIES_CLASSES`; lists, rankings, broadcast slots and editorial collections are not). Three studios' whole film canons, typed as animated film series on Wikidata, are excluded by Wikidata id (`NOT_A_SERIES`: Walt Disney Animation, DreamWorks and Ghibli, as the code comment names them).
2. Each series is rolled up through its own P179 and P8345 to the topmost series (the film and the game series of "Resident Evil" become the franchise), but never into a series of more than 80 works (`CAP`; only "Mario" reached it, so its works keep "Super Mario", "Mario Kart" and so on). A series most of whose works are in another one is merged into it, again within the cap.
3. A work with no series gets one by title (`titleSeries` in `src/shared/catalog-rules.js`): a series name of two or more words (not counting a leading article) that the title starts with, followed by the end, a space, a digit, a colon or a dash, or that the title ends with and no colon or dash comes before it ("Return to Silent Hill"). A one-word series name is weaker: it must not be an everyday word, the series must hold a work of the same type, and the title must be the name alone or the name plus a number, colon or dash.

Result: 6,035 of the 26,968 works are in a series and 913 series have two or more works. Resident Evil has 43 works (42 titled with the name, plus Umbrella Corps), Silent Hill 14 (13, plus P.T.) and God of War 9. The largest are Star Wars (65), the Sherlock Holmes canon (64), Pokémon (63), Sonic the Hedgehog (59), Asterix (57) and the Marvel Cinematic Universe (56). `data/catalog.json` grew from 3.69 to 3.86 MB with the series, and to 4.26 MB with the 0.2.4 coverage changes. `test/fixtures/series.json` holds the lists for the three franchises named by the test. Known mistake: a work whose title equals a series name joins the series whatever its type (the novel "The House of the Dead" is in the game series; about three cases are known; a `shortcut` comment in `catalog-rules.js`). "Silent Hill: Townfall" is not in the catalog (13 sitelinks, the catalog needs 15). The series data is only as good as Wikidata's.

### Self-update

Opt-in, off by default. Choose daily, weekly or monthly on the settings page (Data), or press "Update now". An explicit press counts as consent for that one download.

- Schedule: an `alarms` alarm named `catalogUpdate` with period 1,440, 10,080 or 43,200 minutes. After the setting is turned on the first run is about a minute later. The alarm handler checks the setting again before it fetches. Turning the setting off clears the alarm.
- Query: works with at least 15 sitelinks (all types: the lower minimums of the build are not used here) and a date (`P577`, `P580` or `P571`) from January 1 of the year before the bundled catalog's build year onward, including future dates. The type is decided locally from the bundled class list. Then labels are fetched in batches of 200. Works with no date are not fetched. Works that are not told as a story are dropped, by one more query per 200 works. Then years, aliases and characters are fetched.
- Series: new works get a series like the build gives it, with at most 5 extra queries of 200 works (`MAX_SERIES_QUERIES`): their Wikidata series ids are mapped through the catalog's own `series` table, and works with none (or all of them when Wikidata fails or the budget runs out) get the title fallback. A series the catalog does not know is not added.
- The `other` lookup: names go to Wikidata in batches of 150, a label query and, for names of one or two words, an alias query. At most 20 queries per update. When the budget runs out or Wikidata fails, a name that was not looked up is treated as `other` if it has one or two words. That is the fail-safe: a wrongly weak title costs less than a wrongly covered news post.
- Client: POST to `https://query.wikidata.org/sparql`, one query at a time, no cookies, no referrer, 90 second timeout. On HTTP 429 or a 5xx response it waits (honouring `Retry-After`, capped at 120 seconds) and tries up to 3 times, then gives up until the next interval.
- Result: the bundled catalog, all added works and the hand-added works are rebuilt with the same code as the Node build (`src/shared/build-index.js`). The index is written to `storage.local` as one key (`catalogIndex`) in a single `set` call, so a tab sees either the old or the new index. Open tabs swap indexes on `storage.onChanged`.
- Failure: only `catalogMeta.lastError` is written. The working index is not touched.
- When the extension itself is updated with a newer bundled catalog, the index is rebuilt offline from `catalogAdded` and `custom`.
- The settings page shows a line such as "26,968 titles + N new · updated 3 days ago", or the last error.

This is the only network use of the extension. A test build may ship `data/update-config.json` to redirect the update to a local mock. Release builds have no such file.

A first catalog build (`tools/catalog/build.mjs`) sends up to about 800 more queries than before for the `other` lookup: the names go into 400 fixed buckets, each with one or two queries. Results are cached by query text.
